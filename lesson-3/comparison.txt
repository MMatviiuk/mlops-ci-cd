# Порівняння Docker-образів: fat і slim

## Розміри образів

| Образ   | Базовий образ   | Розмір (факт)                     | Шари |
|---------|-----------------|-----------------------------------|------|
| ml-fat  | python:3.9      | 1,569,830,155 bytes (~1.57 GB)    | 18   |
| ml-slim | python:3.9-slim | 212,508,092 bytes (~212.5 MB)     | 14   |

Розміри отримано після `docker build` на Mac з Apple Silicon.
Команди для перевірки:

```bash
docker image inspect ml-fat --format '{{.Size}}'
docker image inspect ml-slim --format '{{.Size}}'
docker history ml-fat
docker history ml-slim
```

Обидва образи перевірені запуском `inference.py` на одному й тому самому
тестовому зображенні. Результат в обох випадках однаковий.

## Проблеми fat-образу

- Це великий образ для локальної перевірки. Крім базового набору для inference,
  всередині залишаються `Django`, `jupyterlab`, `numpy`, `pandas`, `matplotlib`,
  `scikit-learn`, `scipy`, `opencv-python-headless`.
- Усередині також залишено системні інструменти `curl`, `git`, `vim`, `tree`,
  `ffmpeg`, `build-essential`, `gcc/g++`. Для локальної перевірки вони зручні,
  але для фінального запуску зайві.
- Додатково збережено wheel-файли в `/opt/wheels`, тому образ зручний для
  повторного встановлення пакетів офлайн, але стає суттєво важчим.
- Повний `python:3.9` образ сам по собі помітно важчий за `python:3.9-slim`
  і тягне за собою більше системних компонентів.

## Переваги slim-образу

- `python:3.9-slim` у фінальному етапі містить тільки те, що потрібно для запуску.
- Завдяки multi-stage збірці Python-залежності готуються окремо, а в фінальний образ
  копіюється лише потрібне середовище.
- У фінальному образі немає `apt`, компіляторів, зайвих утиліт і кешу,
  тому він менший, безпечніший і швидше завантажується.

## Присутність зайвих інструментів

- `ml-fat`: містить додаткові пакети, shell-утиліти, компілятори та wheel-файли.
- `ml-slim`: не містить зайвих системних інструментів і зосереджений лише на запуску моделі.

## Пропозиції щодо подальшої оптимізації

1. Перейти на CPU-only колеса PyTorch, якщо модель запускається тільки на CPU.
2. Використати distroless або ще компактніший runtime-образ без shell та package manager.
3. Не переносити додаткові інструменти у фінальний образ, а залишати їх тільки на етапі збірки.
4. Не зберігати wheel-файли у фінальному образі, якщо офлайн-встановлення не потрібне.
5. Копіювати у фінальний етап тільки `inference.py`, `model.pt`,
   `imagenet_labels.json` та мінімальний набір Python-пакетів.
